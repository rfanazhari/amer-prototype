[Service]

Name: amer-prototype

Purpose: Boilerplate Go service for the AI Interview Agent challenge project (the "amer" prototype), generated by gonesis with the Task Tracking reference feature as the architecture and TDD example. The interview prototype itself is NOT part of this run.

Target directory and status: repository root, a new service (the repository is the service).

Module path: github.com/rfanazhari/amer-prototype

Runtime: HTTP JSON API; no authentication, ownership, assignment, or other integrations.

Optional constraints and requested Git actions: Follow the target's compatible Go toolchain and the workflow's standard library selection policies. Use a dedicated worktree. Do not commit or create an MR. Local Dockerfile, Compose, and Makefile artifacts are now in scope by the owner amendment. Remote image publication, provisioning, and remote deployment remain outside scope. PostgreSQL is enabled in Compose; Redis and RabbitMQ are optional profiles and are not Task runtime dependencies. The owner selected GORM (gorm.io/gorm) as the ORM; the PostgreSQL driver is gorm.io/driver/postgres. Do not implement any interview, voice, OpenAI, sideband, or transcript functionality in this run; those belong to FSD-voice-interview-prototype.md. Keep the four layers extensible so that module can be added later without restructuring.

[1. Persistence]

Storage and driver, if applicable: PostgreSQL through GORM (gorm.io/gorm with gorm.io/driver/postgres). Connection string from the DATABASE_URL environment variable; no secrets in committed files.

Retention and restart behavior: Tasks persist across process restarts. No retention, archival, or deletion policy.

Consistency and failure expectations: Mutations are atomic. Concurrent commands on one task must not bypass state-transition rules (the agent selects and records the mechanism, for example a transaction with a row lock). Rejected commands do not change state or timestamps. Completion persists its state and accepts its event together, or neither happens: if the event queue cannot accept the event, completion fails with the dedicated error and the task stays unchanged; if the database commit fails, no event is published for the uncommitted completion.

Database/schema resources, if applicable: GORM AutoMigrate at startup for the tasks table; no SQL migration files. Rollback path: drop the table manually (accepted for a prototype). The agent defines the table constraints (primary key, not-null columns, status check) and documents them.

[2. Internal events]

Dispatch mechanism: In-process queue with capacity 100 and one consumer. No RabbitMQ or other external broker. Do not add eventmanager merely to satisfy a dependency list.

Event fields and publication point: TaskCompleted contains taskId and completedAt. Publication means acceptance into the internal queue as part of the completion operation. A recording/logging subscriber demonstrates consumption without adding another business feature.

Save/publication failure behavior: If persistence or event acceptance fails, leave the task unchanged. If the queue is full/unavailable, return a dedicated 503 error. Repeated completion of an already-Done task returns 409 and adds no event. Same as the gonesis example.

Delivery, retries, and shutdown: Process accepted events with one consumer. Log subscriber failures; do not automatically retry them or roll back a previously accepted completion. On shutdown, stop new commands, drain accepted work, and release resources (including the database connection) within the total shutdown budget. Report a drain timeout as a shutdown failure.

Durability guarantees: Events are process-local; no durable recovery, external delivery, or exactly-once delivery promise. Unexpected process termination can lose queued events.

[3. Time semantics]

Timezone, representation, and precision: Use UTC instants. JSON timestamps use RFC3339 and millisecond precision; compare canonical values at the same precision. Accept valid RFC3339 offsets and normalize them to UTC. Reject unsupported extra fractional precision rather than silently changing the boundary. Same as the gonesis example.

Due-date validation and overdue boundaries: A dueDate equal to the current system time is allowed. Reject dueDate strictly before now on creation or rescheduling. A task is overdue only when now is strictly after its dueDate and the task is not Done. A task without dueDate is never overdue.

Rescheduling and clearing a due date: A non-Done task may replace or clear its dueDate. For the rescheduling operation, null clears it; an absent dueDate field is invalid. For creation, absent or null dueDate means no due date.

Timestamp ownership and test clock: The system assigns createdAt on creation and completedAt on successful completion. Clients cannot supply these timestamps. Use controllable time in domain/application tests, including exact boundaries and time advancement. The clock is an injected port that later feature modules reuse.

[4. API contract]

Transport and operations/routes: HTTP JSON. POST /tasks creates a task; POST /tasks/{id}/start starts it; POST /tasks/{id}/complete completes it; PATCH /tasks/{id}/due-date reschedules or clears the date; GET /tasks/{id} returns details. GET /health is unauthenticated. No list, delete, or title-edit endpoint. Routes for the interview prototype are defined later in the FSD under /api/sessions and must not collide with the routes above.

Identifier and state representation: Generate UUID string identifiers on the server. Serialize states as todo, in_progress, and done. A malformed UUID is invalid input; a well-formed UUID that does not exist is not found.

Request and response fields: Create accepts title and optional dueDate. Start/complete have no request fields. Reschedule accepts dueDate. Task details contain id, title, status, dueDate, overdue, createdAt, and completedAt. dueDate and completedAt remain present as null when unset. Successful task operations return the resulting task details in data; health returns data: {}.

Input boundaries and validation: Trim leading/trailing Unicode whitespace from title, store the trimmed value, and count Unicode code points after trimming. Accept 1-100 code points; reject whitespace-only or overlong titles. Reject unknown request fields and client-supplied identifiers, states, or system timestamps. Start/complete accept no body or an empty object only.

Success statuses and health: Create returns 201; start, complete, reschedule, and details return 200. GET /health returns 200 with status: success and data: {}. Use the standard envelope for all HTTP paths, including validation, routing, and method errors. Health indicates HTTP readiness only (not database or third-party reachability).

Error statuses and response data: Use 400 for malformed input, invalid title/date/identifier, or unexpected request fields; 404 for a missing task or unknown route; 405 for an unsupported method; 409 for a forbidden state transition or modification of Done; 503 for completion-event acceptance failure; 500 for unexpected technical failures. All failures use status: error, data: {}, a dedicated error code, and a safe message. Localize messages in EN/ID; log technical causes internally.

[5. Verification]

Required business/API checks: Demonstrate RED/GREEN for BR-01-BR-09 and all reference acceptance scenarios. Cover concurrent transition correctness and atomic state/event acceptance in relevant checks. Demonstrate create-start-complete-view, rescheduling/clearing, not found, rejected Todo-to-Done, and attempted mutation of Done through the real API. Use controlled time for exact boundary/overdue evidence.

HTTP smoke and lifecycle expectations: Use a go test integration harness that starts the actual composition root on a local listener, verifies unauthenticated GET /health and its JSON envelope, then verifies bounded shutdown and accepted-event draining. Check API routing, validation, and technical error envelopes as applicable.

Architecture constraints: Keep domain, application, delivery, and infrastructure directly at the service root. Domain must not depend on HTTP/database/broker adapters (including GORM). Supply repeatable dependency-direction checks and public domain tests proving that invariants are enforced without handlers or runtime storage. The owner additionally requires documentation for every authored named struct/type, function, and method, including interface methods and test helpers; generated mocks retain generator-provided documentation. The structure must accept an additional feature module (the interview prototype) later without changing the four-layer layout.

Available local resources and execution limits: Go/tool dependencies may be installed through the environment's normal permission process. Loopback networking is available. A PostgreSQL instance is required for repository and API-flow checks: UNRESOLVED - the owner must state which local instance (host, port, database name) the agent may use; credentials are supplied only through environment variables and never written to files. Core Go checks must not require Docker. The owner has now authorized local Docker Compose resources for integration verification; do not require a broker, remote credentials, or remote service mutations. If no PostgreSQL instance is available, report the dependent checks as blocked, not passed. Allow at most 5 seconds for complete shutdown.

Verification evidence expected: Record exact commands and results for all-package checks, unit tests/race checks, lint, security, architecture checks, API flow, and health smoke. Include rule-to-test mapping, RED/GREEN evidence, and any limitations. The agent discovers or creates the concrete commands and test-package paths.
