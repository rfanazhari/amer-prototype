# Todo and gaps: Interview Runtime

Open items found while implementing `CORE-IRT-020`. Each names the decision or scope it needs. None is claimed done.

| ID | Gap | Why it matters | Needed |
| --- | --- | --- | --- |
| G1 | The position is hardcoded as `Project Manager` in `interviewusecase/instructions.go`. The template configuration has no position title, and the local job-description reader returns an unrelated demo role. | Another assignment would tell the model the wrong position. | A `positionTitle` in the template configuration, pinned in the published revision. This changes the configuration schema, validation, API contract and docs. Then remove the constant. |
| G2 | Scope rules are prompt-level only. Nothing detects or records an off-topic candidate turn. | A prompt reduces but does not guarantee scope. Off-topic turns could still be treated as answers. | Transcript classification so off-topic turns are not cited as answers (T13/T14, blocked by Q1). |
| G3 | Instructions are now sent at create and again by `session.update` after attach. Nothing reads the sideband reply, so a rejected update is invisible. The `session.update` frame shape is not verified against the provider. | Duplicate delivery hides which path works. | One reviewed live session that records event types around the update. Then keep one path or document why both stay. |
| G4 | Nothing triggers the model to speak first. The opening line is an instruction only. | The model may wait for the candidate. | Verify in a live session. A provider control event needs the reviewed event map (Q1). |
| G5 | The candidate notice does not say the conversation is limited to the interview. | Candidates may expect general help. | Owner decision. A new notice version changes the consent contract and docs. |
| G6 | Q1 (event finality) may favor a cascaded STT, LLM, TTS design. | Continuous mode leaves finality to the provider. | Decide after the S1 record. The affected layers are listed in the conversation notes, not in this design. |
| G7 | Nothing moves the interview between stages. `Propose` and `OpenStage` exist in the application layer but have no caller, no route and no event reader. The model alone decides when a stage ends, in conversation only. Handoff, `ActivateStage` and `Finish` never run, and the execution never completes. | Stage order, timing and completion are not enforced, and the candidate page only offers cancel. | A trigger for "stage done". Preferred: a model function call carried over the sideband, validated by the backend (next stage only, hard deadline, idempotent). The browser must not choose the stage. |
| G8 | Provider function-call support. Per the OpenAI docs read on 2026-11-03 (not yet tried on our account): `gpt-live-1` lists function calling, but custom functions are documented only under Responses delegation, set at create as `delegation: {type: "responses", responses: {model, instructions, tools}}`; delegation needs a backend model and is billed separately. Completed calls arrive as nested `response.output_item.done` inside `response.event` envelopes (fields `call_id`, `name`, `arguments`) on the sideband or primary websocket; results go back with `response.item.create` (`function_call_output`) then `response.create`. A session is ended with `session.close` and `session.closed`. | G7 and G12 depend on it. Our create payload has no `delegation`, so adding a tool changes the session shape and cost. | One sanitized live spike on our account: create with delegation and one function tool, confirm the event reaches the sideband, return a result, then close. Record event types only. It can double as the S1 record for Q1. |
| G9 | `Authorize` requires resolved coverage, and coverage only changes from final transcript. Decided 2026-11-03 (owner `rfanazhari`): transcription is not per stage but at the end of the interview, and a stage is complete when the model states it. Implemented in T21 as `Progress.Attest` (order, stage clock and hard deadline checked; no coverage) beside the strict `Authorize` path. Restoring a snapshot no longer requires coverage on sealed handoffs. | A statement is not evidence that a question was answered. The report must label such stages as model-stated, and coverage is analysed after the interview. | Wire the trigger (T21 provider part, G8). Revise `BR-CORE-064` and the design text that still says a handoff needs coverage. Reporting Q4 records the effect on report admission. |
| G10 | Per-stage provider sessions cost a new WebRTC negotiation at each handoff (about 2.4 seconds for session setup, plus an audio gap). | The candidate hears a pause at every stage change. | Decide between a new session per stage and `session.update` on one session. The second changes the Q2 policy and the stage-session design. |
| G11 | At the closing stage the candidate asked questions. The model answered that it had no information (scope rule) and nothing was kept. The owner expects those questions to become interview notes for HR. Nothing stores conversation content today, and the end-of-interview transcript (G9 decision) is not built. | A promise to "note" a question is only true once the end-of-interview transcript exists. | Interim: wording only, so the model acknowledges and says the recruitment team will follow up, without answering. Real fix: the transcript step, or a structured note through a model function call (needs G8). |
| G12 | **Partly resolved 2026-11-03:** a candidate Selesai control now completes the interview (CORE-IRT-021; live proof pending); the model-triggered ending still waits for G8. Original gap: the interview can end only by the candidate pressing Cancel, which records CANCELLED. A finished interview is therefore stored as cancelled, and the model cannot end the session even when it says the interview is complete. `Finish` exists in the application layer but no route, page control or model trigger calls it. | Completion state, `Admit` for the report (reporting Q4) and the notice wording ("stopped interviews are recorded as cancelled") are all wrong for a normal ending. | A completion path. Options: a candidate-visible finish control that calls a new route to the lifecycle completion (simple, no provider dependency, new public contract), or a model function call over the sideband (G8). Both change `Authorize`/completion rules (G9). |
| G13 | `SupplyContext` sends `session.update` with `session.instructions`. The docs say frontend instructions are fixed after startup and `session.update` does not change them; context after startup goes through `session.instructions.append` (500 tokens at most per event) or, under Responses delegation, `session.update` on `session.delegation.responses`. Settings errors arrive as events and the session stays open, and nothing reads our sideband. | The post-attach update in create and the reconnect recovery context are probably ignored, silently. Create-time instructions work, which matches the live sessions. | After the G8 spike: replace the update with the documented append event, size recovery context to 500 tokens, read error events, and await `session.closed` after `session.close`. |
| G14 | Transcription at the end of the interview needs a source. GPT-Live offers no documented way to fetch a closed session's transcript by id; transcript arrives as streaming events (`session.input_transcript.delta`, `session.output_transcript.delta`) while the session is open, and the session id is only used to attach the sideband. Decided direction (owner, 2026-11-03): a sideband reader stores the raw transcript events during the session and assembles them after `session.closed`. | Without a sideband reader connected for the whole session, that part of the transcript is lost. The reader also serves model-triggered completion (G8) and error events (G13). Reporting Q4 needs the transcript owner and ordering. | A ticket and owner for the sideband reader and transcript assembly, a decision on what happens to a gap when the connection drops (reconnect, T15), a retention rule, and reporting Q4. |
