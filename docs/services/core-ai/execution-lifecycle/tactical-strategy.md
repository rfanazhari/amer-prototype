# Tactical Strategy: Execution Lifecycle

## 1. Implementation Strategy

Mode A, additive, in the existing Go module. Implement the assessed [technical design](technical-design.md) for [BR-CORE-050..BR-CORE-059](../business/capabilities/execution-lifecycle.md). Do not treat the current execution pin as that lifecycle.

Keep Task, administrative access, candidate access, agent configuration, and the unmounted pin tests behaving as they do today. Add `migrations/pgsql/000008_execution_lifecycle.{up,down}.sql` and raise the clean startup floor from 7 to 8 in the same change that publishes the SQL. Do not register AutoMigrate. Do not add an HTTP route, a voice worker, or a broker consumer.

Ship the shared execution tables and the interview `Start` path together. `Start` is the only interview writer that inserts both `agent_executions` and `interview_executions`. `Admit` proves a non-interview caller can commit the same states without a pin. Leave `agentbindingusecase.StartExecution` unmounted. Do not extend it into a state machine.

The capability status stays planned until the tasks in the task plan have actually been run. This strategy does not mark any rule enforced.

2. SQL version 8 and the startup floor (T3), before any release-schema repository test.
3. GORM adapter (T4) and application operations (T5, T6, T7). Application tests use mocks and can land beside the adapter.

## 5. Testing Strategy

Commands are the Makefile targets. `make test` is the domain and application race check. `make test.contract` must show the OpenAPI document unchanged in behavior. `make test.architecture` covers imports and declaration comments. `make lint` is required on the gate. Locking, rollback, and idempotency need `make test.integration` or `make test.docker`. A package test that skips because `TEST_DATABASE_URL` is unset is not database evidence. Do not point that variable at a database that is not an authorized disposable target.

Existing evidence, not lifecycle proof: `TestAgentConfigurationBindingConsumers` and the pin unit tests show a revision copy. They do not show `CREATED`, fencing, or terminal behavior. No RED/GREEN history is claimed for this capability.

### Unit tests

- Domain, table-driven, public behavior only, factories rather than raw literals: each legal edge; each illegal edge; terminal sources reject later writes; `Complete` without a progress reference fails; binding equality; generation fence; exact deadline instant is late; snapshot copies do not alias time pointers; `RestoreExecution` accepts a backfilled `CREATED` shape and rejects a `COMPLETED` shape with no progress reference.
- Application, Mockery mocks: same key returns the first execution; different fingerprint does not replace it; second key on the same assignment returns the original; `Start` copies the assignment revision even when a newer active revision is on the instance port; revoked assignment inserts nothing, and a running row is cancelled in that transaction; rollback returns no success; uncertain commit returns `EXL_UNCERTAIN_COMMIT`; `Activate` does not allocate a new execution; failed activation stays `CREATED`; `Complete` is refused when the progress port is false; stale generation writes nothing; repeated terminal command returns the first outcome; a different terminal command conflicts.
- sqlmock: insert column list, update column list omits binding columns, assignment lock SQL precedes the execution lock, zero `RowsAffected` is handled. sqlmock is not the concurrency proof.

### Integration tests

- Happy path: migrate to 8, `Start` one assignment, read `CREATED`, `Activate` to `RUNNING`, commit progress, `Complete`. Pin revision equals the assignment revision. A later change to `active_revision_id` leaves both rows.
- Idempotency: repeat `Start` with the same key; a second key for the same assignment; two concurrent starts; unique pin still one row.
- Conflict: same key, different input reference, no replacement.
- Rollback: failure after the execution insert and before commit leaves neither the execution nor the pin.
- First terminal commit: two sessions, completion and cancellation, one terminal value remains.
- Revocation fixture: set `access_revoked_at`, call `CancelNonterminal`, observe `CANCELLED`. A second call does not reopen it. `Start` on that assignment does not insert another execution.
- Authority expiry: the same operation with reason `authority_expired` cancels a nonterminal row. This does not prove a real session clock called it.
- Backfill: a version-7 pin row upgraded by `000008` is `CREATED`, same id, same revision, null activation and progress.
- `Admit`: one execution and no `interview_executions` row can reach `COMPLETED` when the progress port is true.
- Reporting surface: the query interface has no complete or cancel method. A direct update of a `COMPLETED` row through the mutation port is rejected.
- Invitation issue source does not call the cancel operation.

### Regression tests

- `make test` and `make test.all` still pass for Task, access, and configuration.
- `make test.contract` passes with no new public path.
- The private-table pin preservation test still passes.
- Startup on clean version 8 succeeds and startup on clean version 7 fails.
- A disposable down of one step removes only the version-8 objects and leaves `interview_executions` in place, then up restores them. Do not run that down on a retained database.

## 6. Rollout & Rollback

- Rollout: stop writers, back up any populated database, apply `make migrate.up MIGRATION_VERSION=8`, require `version=8 dirty=false`, then start the binary. Local Compose uses the same order already documented for version 7, with the target changed to 8. There is no feature flag. No HTTP behavior changes until a sibling calls the operations. No seed job runs.
- The runtime role needs CRUD on the five new tables before the binary serves traffic. The migration role remains the only DDL role.
- Rollback trigger: a failed up, a dirty version, or a binary that cannot read the new rows. Stop rollout. Do not clear the dirty flag as a repair.
- Populated recovery: restore the backup, or ship a forward repair. `migrate.down` is not that repair.
- Application rollback after a successful up: run a binary that accepts clean version 8. The previous version-7 binary will refuse the database. Unmounting is unnecessary because this slice adds no route; siblings simply must not call the operations if the slice is being withdrawn in code while the tables remain.
- Disposable rehearsal: `make migrate.down MIGRATION_STEPS=1 MIGRATION_DISPOSABLE=yes` then `make migrate.up MIGRATION_VERSION=8`.
